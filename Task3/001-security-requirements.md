# Требования к внешней интеграции с платформой "Умный дом"

## 1. Требования безопасности

### 1.1 Шифрование данных

#### 1.1.1 Encryption in Transit
- **REQ-SEC-001**: Все API запросы MUST использовать TLS 1.3 (минимум TLS 1.2)
- **REQ-SEC-002**: Сертификаты платформы партнёра MUST быть выданы доверенным CA
- **REQ-SEC-003**: Certificate pinning в мобильном приложении для защиты от MITM
- **REQ-SEC-004**: Отключить небезопасные cipher suites (RC4, DES, 3DES, MD5)

**Обоснование**: Передача биометрии (специальная категория ПДн по 152-ФЗ ст. 11) требует защиты от перехвата. TLS 1.3 устраняет уязвимости TLS 1.2 (Heartbleed, POODLE).

#### 1.1.2 Encryption at Rest
- **REQ-SEC-005**: Биометрические шаблоны в Smart Home DB MUST быть зашифрованы (AES-256-GCM)
- **REQ-SEC-006**: Государственные номера автомобилей MUST быть зашифрованы (AES-256-GCM)
- **REQ-SEC-007**: Ключи шифрования MUST храниться в отдельном KMS (HashiCorp Vault / AWS KMS)
- **REQ-SEC-008**: Ротация ключей шифрования: ежегодно

**Обоснование**: Требования 152-ФЗ для специальных категорий ПДн (биометрия). Приказ ФСТЭК № 21 от 18.02.2013 - шифрование ПДн УЗ-1 (биометрия).

### 1.2 Минимизация данных (Data Minimization)

**Проблема**: "Контракты API содержат категории данных, которые явно предоставляют персональные данные".

- **REQ-SEC-009**: API контракты MUST передавать только минимальный набор данных, необходимый для выполнения операции
- **REQ-SEC-010**: Платформа партнёра НЕ ДОЛЖНА получать:
  - ФИО собственников (только `tenant_id` - внутренний UUID)
  - Телефоны, email собственников
  - Адреса квартир (только `apartment_id` - UUID)
  - Сырые биометрические данные (только хеши/шаблоны)
- **REQ-SEC-011**: Биометрические шаблоны лиц MUST передаваться в виде хешей (не JPEG/PNG лиц)
- **REQ-SEC-012**: Государственные номера автомобилей SHOULD передаваться в виде хешей SHA-256 (если платформа партнёра поддерживает)

**Обоснование**: Принцип минимизации данных (152-ФЗ ст. 5 п. 5). Снижение риска утечки ПДн. Использование псевдонимов (UUID) вместо реальных данных.

### 1.3 Tenant Isolation (Изоляция данных партнёров)

**Проблема**: "партнёр из одной управляющей компании может увидеть или изменить данные клиентов и жилищных комплексов, которые относятся к другой компании".

- **REQ-SEC-013**: API Gateway MUST проверять `tenant_id` в JWT токене при каждом запросе
- **REQ-SEC-014**: Smart Home Integration Service MUST фильтровать данные по `tenant_id` на уровне SQL (Row-Level Security в PostgreSQL)
- **REQ-SEC-015**: Один партнёр НЕ ДОЛЖЕН видеть/изменять данные других партнёров
- **REQ-SEC-016**: Платформа партнёра MUST возвращать данные только для того ЖК, к которому выполнен запрос

**Обоснование**: Предотвращение несанкционированного доступа (152-ФЗ ст. 19). Защита от случайного или преднамеренного доступа к чужим данным.

### 1.4 Аудит и логирование

- **REQ-SEC-017**: Все операции с биометрией MUST логироваться (создание, изменение, удаление шаблонов)
- **REQ-SEC-018**: Все события открытия дверей/шлагбаумов MUST логироваться
- **REQ-SEC-019**: Логи MUST содержать: timestamp, user_id, tenant_id, operation, IP address, user agent
- **REQ-SEC-020**: Логи MUST храниться минимум 3 года (требование 152-ФЗ для специальных категорий ПДн)
- **REQ-SEC-021**: Логи MUST отправляться в централизованный Audit Log Service (Elasticsearch)
- **REQ-SEC-022**: Неудачные попытки аутентификации MUST логироваться и алертить после 5 неудач за 15 минут

**Обоснование**: Требования 152-ФЗ ст. 19 - учёт доступа к ПДн. Расследование инцидентов безопасности (предотвратить утечку как у конкурента).

### 1.5 Rate Limiting и защита от DDoS

- **REQ-SEC-023**: API Gateway MUST применять rate limiting:
  - 100 запросов/минуту на один `tenant_id`
  - 1000 запросов/минуту на один IP адрес
  - 10000 запросов/минуту на всю систему
- **REQ-SEC-024**: При превышении лимита: HTTP 429 Too Many Requests с заголовком `Retry-After`
- **REQ-SEC-025**: Защита от credential stuffing: блокировка IP после 10 неудачных попыток аутентификации за 5 минут

**Обоснование**: Защита от DDoS атак, злоупотребления API, credential stuffing.

### 1.6 Защита от инъекций

- **REQ-SEC-026**: Все входные данные от платформы партнёра MUST валидироваться (JSON Schema validation)
- **REQ-SEC-027**: SQL запросы MUST использовать Prepared Statements (защита от SQL Injection)
- **REQ-SEC-028**: Запрещено выполнение динамических SQL запросов с пользовательским вводом
- **REQ-SEC-029**: Input sanitization для всех строковых полей (защита от XSS, если данные отображаются в UI)

**Обоснование**: OWASP Top 10 - Injection attacks.

### 1.7 IP Whitelisting

- **REQ-SEC-030**: API Gateway SHOULD ограничить доступ только с IP адресов платформы партнёра (опционально для входящих запросов от PropDevelopment)
- **REQ-SEC-031**: Webhook от платформы партнёра (если используются) MUST приниматься только с whitelisted IP

**Обоснование**: Дополнительный уровень защиты от несанкционированного доступа.

### 1.8 Обработка биометрических данных

- **REQ-SEC-032**: Биометрические данные (лица) MUST обрабатываться только после получения явного согласия собственника (152-ФЗ ст. 11)
- **REQ-SEC-033**: Собственник MUST иметь возможность отозвать согласие и удалить биометрические шаблоны
- **REQ-SEC-034**: При удалении собственника все биометрические шаблоны MUST быть удалены в течение 24 часов
- **REQ-SEC-035**: Биометрические шаблоны НЕ ДОЛЖНЫ покидать пределы РФ (152-ФЗ ст. 12 - трансграничная передача)

**Обоснование**: 152-ФЗ ст. 11 - обработка биометрических ПДн только с согласия субъекта. Единая биометрическая система (ЕБС) РФ.
