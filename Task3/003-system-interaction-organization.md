## 3. Организация взаимодействия между системами

### 3.1 Архитектурный паттерн

**REQ-INT-001**: Использовать паттерн **API Gateway + Backend for Frontend (BFF)**

**Обоснование**:
- API Gateway решает проблемы безопасности партнёров
- Единая точка входа для аутентификации, авторизации, rate limiting
- Упрощает мониторинг и логирование всех внешних запросов

**REQ-INT-002**: Smart Home Integration Service - единственный компонент, взаимодействующий с платформой партнёра (изоляция внешней зависимости)

### 3.2 Протоколы взаимодействия

#### 3.2.1 Синхронное взаимодействие (REST API)

**REQ-INT-003**: Использовать REST API для синхронных операций:
- Управление доступом (добавить/удалить лицо, номер автомобиля)
- Открытие двери/шлагбаума по требованию
- Получение статуса устройств

**REQ-INT-004**: API версионирование через URL: `/api/v1/intercom`, `/api/v2/intercom`
**REQ-INT-005**: Формат данных: JSON (Content-Type: application/json)
**REQ-INT-006**: HTTP методы:
- `GET` - чтение данных (идемпотентный)
- `POST` - создание ресурса (не идемпотентный)
- `PUT` - полное обновление (идемпотентный)
- `PATCH` - частичное обновление (идемпотентный)
- `DELETE` - удаление (идемпотентный)

**REQ-INT-007**: HTTP коды ответа:
- `200 OK` - успешная операция
- `201 Created` - ресурс создан
- `400 Bad Request` - некорректные данные (с детальным описанием ошибок)
- `401 Unauthorized` - отсутствует/невалидный токен
- `403 Forbidden` - недостаточно прав
- `404 Not Found` - ресурс не найден
- `409 Conflict` - конфликт (например, биометрический шаблон уже существует)
- `429 Too Many Requests` - превышен rate limit
- `500 Internal Server Error` - ошибка сервера
- `503 Service Unavailable` - сервис недоступен (maintenance)

**REQ-INT-008**: Формат ошибки (должен содержать: error code, message, details, timestamp, request_id)

#### 3.2.2 Асинхронное взаимодействие (Webhook или Message Queue)

**REQ-INT-009**: Для событий от устройств (door_opened, face_recognized, license_plate_scanned) использовать асинхронную доставку:
- **Вариант 1**: Webhook от платформы партнёра → API Gateway → Smart Home Integration Service
- **Вариант 2**: Polling (Smart Home Integration Service периодически опрашивает платформу партнёра)

**REQ-INT-010**: При выборе Webhook:
- Платформа партнёра MUST повторять доставку при ошибке (exponential backoff: 1s, 2s, 4s, 8s, 16s)
- API Gateway MUST отвечать 200 OK в течение 5 секунд (иначе партнёр считает доставку неудачной)
- Обработка событий SHOULD быть идемпотентной (повторная доставка не создаёт дубликаты)

**REQ-INT-011**: При выборе Polling:
- Polling interval: 30 секунд (компромисс между latency и нагрузкой)
- Использовать ETag / Last-Modified для экономии трафика


### 3.3 Обработка ошибок и retry logic

**REQ-INT-012**: Smart Home Integration Service MUST повторять неудачные запросы к платформе партнёра:
- Exponential backoff: 1s, 2s, 4s, 8s, 16s (максимум 5 попыток)
- Повторять только идемпотентные операции (GET, PUT, DELETE)
- Не повторять POST (может создать дубликаты), вместо этого использовать idempotency key

**REQ-INT-013**: Idempotency key для POST запросов (платформа партнёра проверяет: если запрос с таким ключом уже был обработан, возвращает результат предыдущей операции)

**REQ-INT-014**: Circuit Breaker паттерн:
- Если платформа партнёра недоступна (5 неудач подряд) → переключить в состояние "OPEN" (не отправлять запросы 60 секунд)
- После 60 секунд → переключить в "HALF_OPEN" (отправить 1 тестовый запрос)
- Если тестовый запрос успешен → "CLOSED" (нормальная работа), иначе → снова "OPEN"

**REQ-INT-015**: Timeout для запросов к платформе партнёра:
- Connection timeout: 5 секунд
- Read timeout: 30 секунд (для операций открытия двери)
- Total timeout: 60 секунд

**REQ-INT-016**: Graceful degradation:
- Если платформа партнёра недоступна, мобильное приложение SHOULD показывать последнее закешированное состояние устройств
- Критичные операции (открытие двери) MUST работать через fallback механизм (например, локальный контроллер на устройстве)

### 3.6 Мониторинг и алертинг

**REQ-INT-017**: Мониторинг метрик (Prometheus + Grafana):
- Latency запросов к платформе партнёра (p50, p95, p99)
- Error rate (% неудачных запросов)
- Throughput (запросов/секунду)
- Circuit breaker state (OPEN/HALF_OPEN/CLOSED)

**REQ-INT-018**: Алерты:
- Error rate > 5% за 5 минут → уведомление в Slack/PagerDuty
- p95 latency > 2 секунды → уведомление
- Circuit breaker OPEN > 5 минут → критичный алерт

**REQ-INT-019**: Health Check endpoint (должен возвращать статус сервиса и зависимостей)

### 3.7 Тестирование интеграции

**REQ-INT-020**: Контрактное тестирование (Pact):
- PropDevelopment публикует контракт API (OpenAPI / Swagger)
- Платформа партнёра реализует контракт
- Автоматическое тестирование совместимости при изменении API

**REQ-INT-021**: Песочница (Sandbox):
- Платформа партнёра MUST предоставить sandbox окружение для тестирования
- Sandbox MUST содержать тестовые устройства (виртуальные домофоны/шлагбаумы)
- Sandbox НЕ ДОЛЖЕН содержать production данные

**REQ-INT-022**: Интеграционные тесты:
- Автоматические тесты для всех критичных сценариев (добавление биометрии, открытие двери)
- Запуск в CI/CD pipeline перед деплоем
